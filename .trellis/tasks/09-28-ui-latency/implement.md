# implement.md — 卡顿调查（只读，未改脚本）

## 结论：卡在同步的外部 IP 探测上，不在你选的那两个功能本身

`src/00-bootstrap.sh` 的 `v4v6_refresh()` 会**串行**发 7 次网络请求，每次 `--max-time 5`：

| 顺序 | 目标 | 用途 |
|---|---|---|
| 1 | `myip.ipip.net` (v4) | 本机公网 IPv4 |
| 2 | `4.ipw.cn` (v4) | 同上（备选） |
| 3 | `icanhazip.com` (v4) | 同上（备选） |
| 4 | `icanhazip.com` (v6) | 本机公网 IPv6 |
| 5 | `6.ipw.cn` (v6) | 同上（备选） |
| 6 | `myip.ipip.net` (v4) | 显示"归属地" |
| 7 | `ip.fm` (v6) | 显示归属地 |

**沙箱实测（把每次探测桩成"超时"，模拟你那台机器连不上这些服务）**：

| 动作 | 耗时 |
|---|---|
| `v4v6_refresh` 冷启动 | **35.0 秒** |
| `v4v6`（无缓存） | 35.0 秒 |
| `v4v6`（缓存新鲜，300s 内） | 0.0 秒 |
| `v4v6`（缓存过期 >300s）→ **主菜单每次重绘走这里** | **35.0 秒** |
| **切换 IP 优先级（只是进去再按 0 返回）** | **35.0 秒** |
| `ipuuid` | 35.0 秒 |
| **更换 UUID（改完到返回）** | **35.1 秒** |
| `sbshare → result() → refresh_saved_ip` | 35.1 秒 |

即使这些服务**能通但慢**（每次 0.5 秒），每处也还要 **3.5 秒**。

## 为什么会波及这么多地方

1. **缓存只在一个入口生效**：`v4v6()` 有 300 秒缓存，但另外三处调用点用的是
   `v4v6_refresh()`（无条件重新探测）：
   - `switch_ip_priority`（`50-client-output.sh:19` 附近）——你点名前那一处；
   - `ipuuid`（同文件 `:48`）；
   - `refresh_saved_ip`（同文件 `:564`）——它被 `result()` 调用，而 `result()` 是所有
     **分享文件刷新**的必经之路：改 UUID、改端口、改密码、启用/停用入口、切 IP 优先级，
     每一步结束都会走一遍 → 于是"换 UUID 也卡"。
2. **主菜单每 5 分钟一次**：`menu()` 每次重绘都调 `v4v6`，缓存一过期就阻塞 35 秒——
   这就是"其它地方也卡"。

## 次要因素（不是主因，但每次操作都在付）

- `commit_config`：重启服务 + `sleep 1` + 查状态 ≈ 1–3 秒（`40-service.sh:511/519`）。
- 固定等待：`sleep 2` 出现在安装/端口确认/分享输出等处，`sleep 1` 出现在证书与菜单分支，
  合计每次操作再多 1–4 秒。
- 更换 UUID 的 35 秒里，真正改配置只占不到 1 秒，其余全是探测 + 分享刷新。

## 建议修法（未实施，等用户决定）

1. **缓存优先 + 后台刷新**：把上述三处改用 `v4v6()`（有缓存就用，不管年龄），
   真探测放后台（`v4v6_refresh &`）不阻塞界面；需要最新 IP 时用菜单里显式的
   "刷新本地IP"入口。→ 这三处立刻变成 0 秒。
2. **让探测本身变快**：`--max-time 5` 收到 2 秒，并把几个候选并发跑、取最先成功的结果。
   → 即使冷启动/显式刷新，最坏也就 ~2 秒，正常 <0.5 秒。
3. 两者都做（推荐）。

调查方式：沙箱里抽出全部函数、桩掉 `curl`（每次 sleep 后返回超时码 28）、`restartsb`、
`service_is_active`，用 `date +%s.%N` 计时；脚本在 `/tmp/latency/measure.sh`，可复跑。
未联网、未改动仓库任何文件。

## 追加：5.1.2 上线后暴露的真实事故与修复（我造成）

**事故**：用户安装 5.1.2 时，`ipuuid` 处打印
`/dev/fd/63: line 229: read_ip_cache: command not found`。

**根因**：上一轮我把 `v4v6_refresh(){…}` 到 `v4v6(){…}` 之间的整块替换掉，
而 `read_ip_cache(){…}` 正好夹在中间，被一起删了。这正是我在这个会话里第三次犯的
"切片替换误删中间块"。当时所有检查都没抓到：

- 门禁：unit/repair 不加载 00-bootstrap（harness 甚至用桩把 `valid_ipv4` 打死），回放当时也没覆盖 IP 路径；
- 我自己的延迟沙箱里 `v4v6`（缓存新鲜）显示 5 秒，我把这个异常解释成"缓存里没有有效地址所以回退探测"
  —— 其实是 `read_ip_cache` 根本不存在。**把异常解释掉，而不是查清楚**，是这次没抓住的直接原因。

**修法（5.1.3）**：
1. 把 `read_ip_cache` 原样放回；
2. 顺手修掉同一路径上的两个真问题：
   - `ipuuid` 的两个"刷新本地IP"分支：探测失败会**把缓存里的 IP 清空** → 选择原地打转；
     而且 `readp` 没保护、EOF 时会死循环。现在：探测失败用缓存兜底、拿不到就明确报错返回、
     `readp` 失败即返回；
   - `v4v6_refresh`：探测失败的家族**沿用上一次的好值**（按家族合并），两个家族都没拿到才什么都不写
     —— 否则一次网络抖动就会把已知 IP 抹掉，连带废掉缓存兜底。
3. **补上能抓住这类问题的门禁**：回放新增 5 条流程（`ip_cache_warm` / `ip_cache_stale` /
   `ip_cache_missing` / `ipuuid_warm_cache` / `ipuuid_probe_fails`，共 22 条），
   每条流程在子进程里带 30 秒超时（挂死＝失败）。
   元验证：再次删掉 `read_ip_cache` → 回放 3 条报红；放回 → 22/22 绿。

**验证**：门禁 394 项全绿；真实内核三项通过；延迟实测四个界面入口 0.0–0.1 秒（修前 35 秒）；
用户场景沙箱复现（有缓存 / 无缓存两种）均 0.02 秒完成、无报错、不打转。
